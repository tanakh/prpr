# prpr design note

## The goal

* Must be sufficiently fast.
* Must allow for intuitive syntax definition.
* Must support both text (`&str`) and binary (`&[u8]`) data.
* Should minimize cloning wherever possible.
* While it is a Packrat parser, it must allow for explicit control over which parts are cached—given that caching inherently introduces performance overhead.
  * Alternatively, it should be designed such that the decision to *not* cache is an informed, deliberate choice.
* Must be capable of handling delimiters and spacing effectively, even without a separate lexer (e.g., through the use of "atomic" directives).
* Must be able to generate error information suitable for diagnostic error reporting, with an API designed for easy integration with existing error-reporting frameworks.
* Must support code generation via `proc-macro`, as well as the generation of standalone Rust files.
* Ideally, it should also be capable of generating standalone source files in other programming languages.
* It should be suitable for generating parsers intended for use within `proc-macro`s.

## Development flow

The parser of the grammar language is generated by prpr from its self-describing grammar, [prpr.peg](../prpr-codegen/src/parser/prpr.peg).
It was bootstrapped with a naive stage 0 parser written with [winnow](https://crates.io/crates/winnow); see [Bootstrap](#bootstrap).

Diagnostics are tested `rustc`-style with [`ui_test`](https://crates.io/crates/ui_test).

## Architecture

### Crates

| crate | role |
|---|---|
| `prpr` | Facade. Re-exports `prpr-runtime` as `prpr::runtime` and the `grammar!` and `include_grammar!` macros. Users of the macro depend on this crate only. |
| `prpr-runtime` | Everything generated code needs at run time. `no_std` + `alloc`, no dependencies. Kept as a single self-contained module so that it can be inlined into generated files. The optional `proc-macro2` feature adds `SourceText` (see below). |
| `prpr-codegen` | Grammar front end, static analysis and the Rust back end. Used by the macro, the CLI and `build.rs` scripts. Depends on `proc-macro2`, `quote` and `prpr-runtime` (for `SourceText`), plus `prettyplease`/`syn` behind the `build` feature, which provides standalone files (`prpr_codegen::file`) and the builder for build scripts (`prpr_codegen::build`). |
| `prpr-macros` | The `grammar! { ... }` and `include_grammar!("file.peg")` proc-macros. Thin wrappers around `prpr-codegen`. |
| `prpr-cli` | The `prpr` command: `prpr gen` writes standalone `.rs` files, `prpr check` reports diagnostics, `prpr runtime` writes the runtime as a module. |

Benchmarks live in `benchmarks/`, a separate workspace so that the libraries compared with stay out of the main one.

The minimum supported Rust version is 1.96. Rust 1.88 stabilized `proc_macro::Span::{start, end, line, column, file, local_file}`, which the macro needs, and Rust 1.96 stabilized `core::range::Range`, a `Copy` range that prpr uses for spans.

### One grammar text, two carriers

A grammar is lexically a subset of Rust tokens, so exactly the same text is valid both in a `.peg` file and inside `grammar! { ... }`.

```
grammar!{}  : TokenStream --(rebuild text from token positions)--> SourceText --+
.peg file   : text (Rust fragments are lexed with proc_macro2) ----> TextSource --+--> Source
                                                                                  |
                 grammar parser (runs on the text; spans are byte ranges) <-------+
                 -> AST -> analysis -> Rust back end -> TokenStream (or pretty-printed file)
```

* The PEG part of a grammar is always parsed as text.
  Rust fragments (rule types, actions, Rust items) are taken as tokens from the `Source`: the original tokens inside a macro, tokens lexed from the text for a file.
  Inside a macro, an action block `{ ... }` is the original `Group`, so errors in user code point at the grammar and rust-analyzer works inside actions.
* In the macro, the text is rebuilt from token line/column information (`Span::start`/`end`), which reproduces the original layout except for comments.
  When positions are unusable (e.g. tokens produced by `macro_rules!`), tokens are separated by single spaces, using `Punct` spacing to keep joint punctuation together.
  The grammar language never depends on whitespace between tokens, so the meaning does not change.
* Diagnostics are byte ranges of the text. The macro maps them back to token spans and emits `compile_error!` with the start and end tokens spanned separately (the technique `syn` uses), which works without the unstable `Span::join`.
* For a file, Rust fragments are lexed at their line and column in the grammar (the text before them is replaced by padding), so `Source::locate` maps their tokens back to byte ranges.
  Syntax errors that `syn` finds in them and unknown `#x`/`@x` are then reported as diagnostics at the grammar; inside a macro, the compiler reports them at the original tokens.
  Type errors in files are reported by the compiler in the generated module, since Rust has no `#line` directive.
* `SourceText` is public (`prpr-runtime`, feature `proc-macro2`), so that users can parse the input of their own proc-macros with a prpr parser and report errors at precise spans.
  `SourceText::with(tokens, f)` runs `f` on the text and turns the `MacroError` it returns (a `ParseError` converts with `?`) into `compile_error!`, and `prpr::define_proc_macro!(name, parser, expand)` defines a whole proc-macro with it.
* `include_grammar!("file.peg")` reads a file as a `TextSource`, relative to the invoking file (`Span::local_file`), and emits `include_str!` of it so that the compiler tracks it.
  Diagnostics are rendered with the file's lines into the message of a `compile_error!` at the path.
  A macro cannot make spans in another file, so errors that only the compiler finds in the Rust code of the file are reported at the invocation, and the names generated for rules get the span of the path, so that the compiler lints them like code the user wrote.

### Grammar language

```rust
use crate::json::Value;              // Rust items are copied verbatim

/// Parses a JSON value.             // doc comments go to the generated function
pub value: Value
    = object / array
    / s:string { Value::String(s) }
    / n:number { Value::Number(n) }
    / "true" { Value::Bool(true) } / "false" { Value::Bool(false) } / "null" { Value::Null }

object: Value = "{" kvs:(string ":" value, ",")* "}" { Value::Object(kvs) }
array: Value = "[" es:(value, ",")* "]" { Value::Array(es) }

#[label = "string"]
atom string: String = '"' cs:character* '"' { cs.into_iter().collect() }
atom character: char = [^ '"' '\\' '\0'-'\x1F'] / "\\" c:escape { c }
```

Rules:

```
[#[attr]]* [pub | pub(...)] [atom] name [: Type] = expr
```

* A rule without a type has the type `()`.
* Types may mention the input lifetime `'i`, e.g. `ident: &'i str = ...`, which allows zero-copy syntax trees.
* A rule ends where the next item starts; no terminator is needed.
* Rule attributes: `#[memo]`, `#[label = "..."]`, `#[boundary(expr)]`, `#[no_boundary]`, doc comments.
  Grammar-level settings use inner attributes, e.g. `#![input = bytes]`.

Expressions, from the lowest precedence:

| syntax | meaning |
|---|---|
| `e1 / e2` | ordered choice |
| `e1 e2 ... { code }` | sequence, optionally ending with an action |
| `e1 e2 ... &{ code }` | sequence ending with a semantic predicate (`code` returns `Option<T>`, `Result<T, E: Display>` or `bool`) |
| `x:e` | binds the value of `e` to `x` |
| `&e`, `!e` | positive and negative lookahead |
| `e*`, `e+`, `e?` | repetition and option |
| `(e)`, `(e, sep)*`, `(e, sep)+` | grouping and separated lists |
| `<e>` | atomic group: no implicit whitespace inside, treated as one token |
| `"lit"`, `r"lit"`, `'c'` | literals (Rust literal syntax and escapes); `b"..."` and `b'c'` with byte input |
| `[a-z '_' '\u{3000}']`, `[^ '"']` | character class: bare characters and Rust character literals, whitespace between them is ignored |
| `.` | any character (any byte with byte input) |
| `rule`, `path::to::rule` | rule reference; a path refers to a rule of another grammar |

Inside action code, `#x` is the input slice matched by the binding `x` (`&'i str` or `&'i [u8]`) and `@x` is its span, a `core::range::Range<usize>`; `#_` and `@_` refer to the whole sequence.
These are recognized at the token level, only when the sigil is not preceded by an identifier, so Rust patterns such as `n @ 1..=9` are left alone.
They are not recognized inside `quote!`-like macros (`quote`, `quote_spanned`, `parse_quote`, `parse_quote_spanned`), where `#x` means interpolation.

#### Values

* A literal has the value `&'static str`, but is *silent*: it is left out of the tuple that a sequence without an action produces.
  A choice whose alternatives are all literals yields the matched literal and is not silent, so `op:("+" / "-")` works.
* A character class and `.` yield `char` (`u8` with byte input).
* A reference yields the rule's value. A reference to a rule without a type is silent.
  A reference to a rule of another grammar is never silent, since its type is unknown when the code is generated.
* A sequence without an action yields the tuple of its non-silent elements (the element itself if there is only one, `()` if there is none).
* `e?`, `e*`, `e+`, `(e, sep)*` yield `Option<T>` and `Vec<T>`. They are silent if `e` is.
* Lookaheads yield `()` and are silent.

Values that are never used (unbound silent elements, elements only referenced by `#x`/`@x`, bodies of rules without a type, lookaheads) are only recognized, without building vectors or running plain actions.
Semantic predicates always run.

### Whitespace, tokens and delimiters

Rules are *syntactic* (the default) or *lexical* (`atom`).

* Inside a syntactic rule, the implicit rule `spaces` is applied before every *token*.
  The tokens are literals, character classes, `.`, references to atoms and atomic groups `<e>`.
  References to syntactic rules are not tokens; the callee skips whitespace before its own tokens.
* `spaces` defaults to `(whitespace / comment)*` with `whitespace = [' ' '\t' '\r' '\n']` and no comments.
  `whitespace`, `comment` and `spaces` can all be redefined in the grammar, and must be atoms.
* Failures inside `spaces` and `whitespace` are never reported as expected tokens, however these rules are invoked, and neither are failures of `comment` at its start; failures after it has started are, so that a comment that cannot end is reported (`Cx` does not record failures at positions up to `quiet_to`).
  They are marked as the expectations of a comment, and only reported where nothing else was expected: a comment that matched may have expected more at its end, e.g. the end of the input after a line comment, which should not mix with the error of what follows.
  Marking them costs nothing while failures are not recorded, unlike rolling back the failures of comments that matched, which slowed comment-heavy input down by 11%.
  The last result of `spaces` is cached, so trying several alternatives at the same position skips whitespace only once.
* Spacing mode is lexically scoped: a lexical rule may call a syntactic rule (e.g. an expression inside string interpolation), which then skips whitespace before its tokens.
  Whitespace after it is up to the lexical rule.
* A reference to an atom or an atomic group is *opaque*, like a token from a lexer: when it matches, what was expected inside it is forgotten.
  So after the number in `[1, 2`, the error is "expected one of `,` or `]`" rather than also listing digits, `.` and the exponent.
  When the token does not match, its inner failures are kept, e.g. for an unterminated string.
* Spans and `#x` slices never include the leading whitespace.
* An entry point for a syntactic rule skips trailing whitespace before checking for the end of the input.

Delimiters are handled by a *boundary* check after each literal, reference to an atom and atomic group in a syntactic rule.
A single character (a class or `.`) is not a word and is not checked.

* By default, if the token ends with a word character and the next character is also a word character, the token is rejected.
  So `"if"` does not match the prefix of `ifx`, and a number token rejects `123xyz` but accepts `123(xyz)`.
  Word characters are defined by the overridable rule `word_char` (default `[a-zA-Z0-9_]`).
  For literals the check is resolved at generation time.
* `#[boundary(e)]` on an atom replaces the default check with "`e` must succeed after the token" (nothing is consumed).
  For example, `#[boundary(![a-zA-Z0-9_.])] atom number = ...` also rejects `123.foo`.
  `#[no_boundary]` disables the check.
* A rejected token is reported as "expected delimiter".

With byte input there are no implicit whitespace and no word characters, so no delimiters, unless the grammar defines them.

Rationale: implicit whitespace, and delimiters after literals, are plain PEG (`spaces "if" !word_char`), but the delimiter check after an atom is not: it depends on the last character the atom matched, and PEGs have no lookbehind.
Making syntactic rules pure syntactic sugar would take a lookbehind primitive in the core, which is deliberately not added: the core stays the plain PEG operators.
Delimiting tokens correctly is what makes lexer-less PEG parsers tedious in practice, so prpr does it implicitly in syntactic rules instead, while atoms remain plain PEG.
If a way to express the check in plain PEG is found (for example with built-in rules), the implicit check is to be replaced by it; it may well not exist.

### Memoization

* Nothing is memoized unless the rule has `#[memo]`.
* Memo tables are fields of a per-parse `Memo` struct generated for each grammar, holding only the tables of `#[memo]` rules.
  There is no global or thread-local state and nothing to clear: the struct is dropped when the parse ends.
* Only memoized rules require `T: Clone`. A missing implementation is reported once, at the rule's type in the grammar.
* To make *not* caching an informed choice:
  * With `#![lint]`, alternatives of one choice that may parse the same syntactic rule at the same position are errors, unless the rule has `#[memo]` or `#[no_memo]`, which states that it is deliberately not memoized.
    It looks at rules in a common start of the alternatives, and at rules that both invoke at their start positions after it, through other rules (from `first_calls`, the analysis behind the left recursion check); only the outermost such rule is reported.
  * With `#![profile]`, rules count their calls, the calls at positions where they were already called, and memo hits, in a `Profile` in the grammar's `Memo`, which implements `Profiled`; `runtime::profile` takes it out after a parse.
    Grammars without the attribute generate no counting code, and `Cx` has no profiling state, so they pay nothing, and the runtime needs no feature (a `cfg` in `rt.rs` would also be evaluated in the crates it is inlined into).
    Only the rules of the profiled grammar are counted, not those of grammars it uses.

### Lints

`#![lint]` reports, as errors, mistakes that are easy to make with ordered choice:

* an alternative after one that always succeeds (judged conservatively: tokens in syntactic rules may fail their delimiter checks);
* an alternative whose start an earlier alternative matches (the earlier one's elements, structurally, with the last possibly a literal that is a prefix of the later one's, unless delimiters tell them apart);
* rules parsed more than once at the same position (above);
* unused private rules: their entry functions deny `dead_code` and get the span of the rule's name, so that the compiler reports them unless Rust code uses them. (It does not lint code that looks generated; with `include_grammar!`, the names get the span of the path, which the user wrote.)

Errors rather than warnings, because stable proc-macros cannot emit warnings; the workaround of using a `#[deprecated]` item reads as a deprecation, which is misleading.

### Generated code and composability

For each grammar the back end generates, in the scope where it is invoked:

```rust
pub fn value<'i>(input: &'i str) -> Result<Value, ParseError>;   // per rule, full match
pub struct Memo<'i> { /* tables of #[memo] rules, whitespace cache, `Memo`s of other grammars */ }
pub enum Rules {}                                                  // raw, composable rules
impl Rules {
    pub fn value<'i>(cx: &mut Cx<'i, str>, m: &mut Memo<'i>, pos: usize) -> Result<(Value, usize), Fail>;
}
```

Entry functions and raw rules have the visibility of their rules; rules without `pub` get private ones.
`runtime::parse_prefix` runs a raw rule on a prefix of the input; `runtime::parse_full`, which runs one on a whole input, is what entry functions call, with the whitespace of their grammar, and is hidden, since other code cannot pass that.

* Rules are plain functions. `Cx` (input and error tracking) is defined by the runtime and shared by all grammars; `Memo` is per grammar.
* `Rules` is a type rather than a module, so that grammars work in function bodies, where a module could not refer to the items of the function, and so that its items have the visibilities written on the rules.
  It is an enum without variants: it has no values, and it does not take the name `Rules` in the value namespace.
  Associated functions cannot be imported with `use`; they are called by their paths.
* A rule of another grammar is referenced by path, e.g. `json::value`.
  The caller's `Memo` embeds the callee grammar's `Memo` automatically, and errors are tracked in the shared `Cx`.
  For each rule, a grammar emits a constant named after it in a hidden `__Rules`, of a type that implements `ForeignRule`: whether the rule is an atom (a constant, so that whitespace is handled at compile time), and a method that parses it, as a token with the boundary check of its own grammar if it is one.
  A reference looks the constant up once and calls the method once, with the kind of input fixed, so that a misspelled or private rule, or one of a grammar of another kind of input, is reported once, at the reference.
  (A generic runtime function doing the same changed what LLVM inlined, and executed 8% more instructions on a benchmark of references; a trait object was devirtualized, but too late to be inlined.)
  Both grammars must use the same runtime and input kind; the compiler checks this.
* Rule bodies are compiled to straight-line code with labeled blocks and `let`-`else`; no closure chains.
  Actions are wrapped in immediately invoked closures so that `return` and `?` stay local to the action.
* The input kind (`str` or `[u8]`) is fixed when the code is generated. Text input is matched byte-wise, and characters are decoded only for non-ASCII bytes.
* Internal identifiers use `Span::mixed_site()` and a `__` prefix.

### Errors

* Errors are reported at the farthest failure position, together with the set of expected items.
* A parse first runs without recording failures, which only costs a branch per failure.
  Only when it fails is the input parsed again, recording what was expected (as rust-peg does).
  So actions may run twice on invalid input.
* `!.` failing reports "expected end of input". Other negative lookaheads are silent.
* `#[label = "..."]` replaces what was expected at the rule's start position, like Parsec's `<?>`; errors deeper inside the rule are kept.
  Nested labels at the same position: the outermost wins.
* A semantic predicate returning `Err(e)` means that its sequence matched but is invalid: what was expected inside the sequence is forgotten, and `e` is reported at its start.
  `None` and `false` only filter: the failures inside the sequence are kept.
* `ParseError` is not generic: `span()`, `expected()`, `found()`, `line_col()`, `Display` (`expected one of ..., found ...`), `core::error::Error`, and a simple rustc-like renderer.
  Byte ranges make it straightforward to pass to ariadne, miette, codespan-reporting or annotate-snippets. In a proc-macro, `SourceText` turns it into `compile_error!`.
* Error recovery is out of scope for now.

### Runtime distribution

* By default, generated code depends on the runtime crate: `::prpr::runtime` from the macro, `::prpr_runtime` from the CLI.
  Many grammars share one runtime.
  Macro output always matches the runtime version, because both come from the same `prpr` release.
  Standalone files check the runtime version they were generated for at compile time.
* `--inline-runtime` embeds the runtime into the generated file, for zero-dependency single grammars and for bootstrapping.
* `prpr runtime -o rt.rs` writes the runtime once, and generated files refer to it with `--runtime-path crate::rt`.
  (The `prpr_codegen::file` module provides the same for `build.rs` scripts.)
* In build scripts, `prpr_codegen::build::compile("src/x.peg")` writes `$OUT_DIR/src/x.peg.rs` and emits `cargo::rerun-if-changed`, and `prpr_runtime::include_parser!("src/x.peg")` includes it (a `macro_rules!` macro, kept out of `rt.rs` so that it is not inlined into generated files).
  Build scripts can show warnings (`cargo::warning=`), which stable proc-macros cannot.
  This gives zero external dependencies without duplicating the runtime across grammars.
* Public API of the runtime:
  * What users need is documented: errors (`ParseError`, `Expected`, `Found`, `LineCol`, `Snippet`), running rules (`parse_prefix` and `profile`), and `Cx` as far as matching input and recording failures go, which is enough to write a matcher by hand.
  * What only generated code uses (`SkipCache`, `MemoTable`, `Predicate`, labels and quiet mode of `Cx`, version checks) is `#[doc(hidden)]`.
    Hiding does not make it free to change: files generated by one `0.x.y` must work with every `prpr-runtime` `0.x.*`, so within a minor version the runtime only adds items.
  * `Expected` is `#[non_exhaustive]`, so that new kinds of expectations are not breaking changes.
* `prpr-codegen` exposes `compile`, `Options`, `Diagnostic` and `Source`, and the `file` module; the AST and the analysis are private.

### Static checks

* Undefined and duplicate rules, rule names that are Rust keywords, duplicate bindings, unknown `#x`/`@x` references.
* Left recursion, direct or indirect, is an error that shows the cycle (`expr -> term -> expr`).
  It is found as a cycle in the graph of rules that may be invoked at a rule's start position, computed with nullability.
  Supporting left recursion (e.g. by seed growing) is future work.
* Repeating an expression that can match the empty input is an error.
  Generated loops also stop when an iteration consumes nothing, as a guard for references to other grammars, which cannot be analyzed.

### Bootstrap

1. Stage 0: a parser for the grammar language written with winnow.
2. The self-describing grammar is compiled into `prpr-codegen` as a standalone file (`src/parser/generated.rs`) with the runtime inlined.
   Changes to the runtime therefore never break the compiler's own parser.
3. After stage 0 and the generated parser were shown to produce the same syntax trees for all grammars in the repository, stage 0 and winnow were removed.
4. A test regenerates the parser with itself and fails if the checked-in file is stale.
   `PRPR_BLESS=1 cargo test -p prpr-cli --test bootstrap` updates it.
   If a change breaks the generated parser, restore it from version control and regenerate.

### Testing

* `ui_test` for compile-fail tests of `grammar!` in `tests/ui` (`cargo test --test ui -- --bless` updates expectations).
* Ordinary `#[test]`s with `assert_eq!` for parsing behaviour.
* The examples of the book (`book/`) are documentation tests of the `prpr` crate: `src/lib.rs` includes each chapter with `#[doc = include_str!(...)]` under `#[cfg(doctest)]`.
  Examples that cannot run are marked `rust,ignore`.
* Benchmarks: a JSON parser compared against other parser generators and combinator libraries ([results](../benchmarks/README.md)).

### Roadmap

1. Runtime core; stage 0 parser; analysis; code generation without memoization; `grammar!`; CLI. (done)
2. Self-describing grammar and bootstrap. (done)
3. `#[memo]` and benchmarks, `#![lint]` and `#![profile]` (done).
4. Byte input, public `SourceText`, cross-grammar references (done); more diagnostics tests.

Later: cut operator (which would also sharpen syntax errors), left recursion, rules with parameters and user state (needed, e.g., for length-prefixed binary data, and for closing delimiters that repeat the opening one, as in raw strings and heredocs, if a parameter can be matched as a literal), case-insensitive literals, error recovery, back ends for other languages (the IR is kept language-neutral; only actions are Rust).

When a need arises: tokens written in Rust, for what grammars cannot express (closing delimiters that repeat the opening one, as in raw strings and heredocs; indentation) or for speed (e.g. `memchr`).
They would be atoms, which need neither memoization nor implicit whitespace, written with the documented part of `Cx`; grammars could refer to them as they refer to the rules of other grammars, through a type like `Rules`.
